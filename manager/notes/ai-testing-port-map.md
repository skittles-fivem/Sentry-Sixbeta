# ai-testing port map

Read-only map of the `ai-testing` branch (converter, encoders/telemetry, viewer) made to plan the Docker web version.
Generated by mapping agents on 2026-10-20 against ai-testing @ 0b53daa. Not yet covered: converter UI inventory, tests/CI run.

## map:converter-backend

### summary

The converter backend (src/main/converter/) is already a pure Node subsystem: none of its 22 files imports `electron`. Everything is dependency-injected through one composition root, `createConverterRuntime(options)` in runtime.js:453. It takes userDataPath, tempPath, ffmpegPath, ffprobePath, spawn, fs, pathApi, platform, and optional overrides removeOwned, renameExclusive, network, factories and gpuDecode. It builds:
- the job store (jobStore.js): a per-job JSON manifest plus an append-only journal;
- the file-transaction manager (staging.js): owned temp files, chunk-journaled copies, separate publication, in-place replacement and rollback;
- the encoder planner (encoderPlanner.js): probes GPU encoders, falls back to CPU;
- telemetry writers and verifier (converterAdapters.js, plus h265Telemetry/av1Telemetry/verifier, which are outside this area but on the same pattern);
- the scanner (scanner.js);
- the job service (jobService.js): discovery producer, N parallel workers, a serialized commit, crash recovery;
- auto-convert (autoConvert.js) and the benchmark (benchmark.js, which reuses the real service in an isolated store).

ipc.js `registerConverterIpc({ipcMain, dialog, service, capabilities, benchmark, auto})` is a thin, well-validated boundary. It registers 17 `converter:*` invoke channels and pushes `converter:progress` and `converter:benchmarkProgress` events. main.js only resolves paths and ffmpeg, wires the lifecycle and IPC, and adds tray and login-item behaviour for auto-convert.

Lifecycle of one clip:
1. **Discovery:** the scanner walks the source and yields Tesla-named .mp4 files and event assets. They are persisted to the manifest in batches, then queued.
2. **Inspect:** ffprobe reads the codec. h265/av1 is skipped as `already-converted`; anything other than h264 fails with `UNSUPPORTED_CODEC`.
3. **Fingerprint and stage:** the source is fingerprinted (sha256 + dev/ino/size). For a network source in auto mode it is copied to local staging in 16 MiB chunks, each journaled twice in the manifest.
4. **Telemetry read:** the H.264 SEI timeline is extracted.
5. **Encode:** ffmpeg runs with GPU decode tiers, then CPU decode, then CPU encoder as fallbacks.
6. **Inject telemetry:** H.265 or AV1 telemetry is written into the candidate.
7. **Verify:** off, quick or full. The verified candidate is moved into a private read-only snapshot.
8. **Commit (one item at a time):** either separate publication (`.partial` file, then a no-replace promotion) or in-place replacement (`TEMP-H265-<name>`, original renamed to `BACKUP-<name>`, TEMP promoted, final validated by hash, backup removed under a guard).
9. **Clean up** owned temp files.

Every step is persisted, so after a crash `store.recover` plus truth tables decide whether to resume, restart, finalize, roll back or stop for manual intervention.

The decisive finding for Docker: on Linux, filesystemTransactions.js provides no owned-file remover and no ownership-checked rename. I ran the real runtime headless in this sandbox (Ubuntu 24.04, ffmpeg 6.1.1-3ubuntu5, the same stack as the target) and it reports `capabilities = {separatePublication:'hardlink-cleanup-pending', ownershipCleanup:'unavailable', replacement:'unavailable'}`. Three consequences:
- **Replace mode is refused.** IPC returns `REPLACEMENT_UNAVAILABLE` and the UI greys the option out.
- **Separate mode leaks.** Every converted clip leaves a `.partial` hard link next to its output and a full copy of the output in `<temp>/sentry-six-verification-*`. With staging (what auto mode picks for an SMB source) it also leaves a full copy of the source in `<temp>/sentry-six-converter`. None of these are ever deleted, so a large archive will fill the container's disk.
- **The fix needs no fork.** Injecting a POSIX `removeOwned`/`renameExclusive` through createConverterRuntime options makes all capabilities available. I verified: replace mode then converted the originals in place to HEVC with no leftovers, crash recovery resumed an interrupted job, and per-frame Tesla telemetry was preserved exactly (24/24 SEI fingerprints identical and in order).

H.265/AV1 itself is not a Linux problem.

### publicApi

RESPONSE ENVELOPE (ipc.js wrapped() L193). Every invoke resolves, never rejects, to {ok:true,value} or {ok:false,error:{code:/^[A-Z0-9_]{1,64}$/,retryable:boolean}}. The renderer's unwrap() (footageConverter.js L107) depends on this. Request payloads go through boundedJsonValue: plain JSON only, whole numbers only, max 64 KiB, max 128 keys per object. For no-payload channels the payload must be undefined; null is rejected with INVALID_REQUEST (I verified this).

INVOKE CHANNELS (ipc.js CHANNELS L9; preload.js L37-80 method names in brackets):
1. converter:chooseFolder [chooseConverterFolder(purpose, defaultPath?)]. Request {purpose:'source'|'destination', defaultPath?:absolute path}. Calls dialog.showOpenDialog({properties:['openDirectory'], defaultPath}). Returns the realpath of the chosen directory, or null.
2. converter:start [startConverter(config)]. Required keys, exactly: sourceRoot, destinationRoot (null if and only if outputMode is replace), codec ('h265'|'av1'), profileId ('conservative'|'balanced'|'aggressive'|'custom'|'quality'), networkMode ('auto'|'staging'|'direct'), outputMode ('separate'|'replace'), includedGroups (non-empty subset of RecentClips/SavedClips/SentryClips), replacementConfirmed (must be true for replace, false for separate).
   - Optional keys: groupOrder (permutation of all 3 groups), concurrency (1-64), bitrateKbps (250-100000, required for custom and only for custom), qualityLevel ('high'|'balanced'|'small', required for quality and only for quality), verifyMode ('off'|'quick'|'full'; off is coerced to quick for replace).
   - Paths are realpath'd. Source/destination overlap returns PATH_OVERLAP. Replace mode requires capabilities.replacement === 'available' (REPLACEMENT_UNAVAILABLE).
   - Returns {jobId: uuid}. Fails with JOB_ACTIVE if any job is in an active state, including paused.
3. converter:getCurrent [getCurrentConverterJob()]. No payload. Returns the sanitized snapshot of the newest active job, else the newest job whose summary was not dismissed, else null.
4-6, 8-9. converter:pause / resume / cancel / retryFailed / dismissSummary [pauseConverter(jobId) etc.]. Request {jobId} (exactly one key). Returns the sanitized snapshot.
   - Errors: JOB_NOT_FOUND, JOB_NOT_PAUSED, RECOVERY_REQUIRED, JOB_ACTIVE, JOB_NOT_RETRYABLE, NO_FAILED_ITEMS, JOB_NOT_COMPLETED.
   - cancel waits for the job's run to finish, which can take a while.
7. converter:discard [discardConverterJob(jobId)]. Request {jobId}. Kills the job (waits up to 30 s), renames job.json to job.json.set-aside-*, and returns the now-current snapshot or null.
10. converter:getCapabilities. Returns {separatePublication:'native-atomic'|'hardlink-cleanup-pending'|'unavailable', ownershipCleanup:'atomic-expected-ownership'|'unavailable', replacement:'available'|'unavailable', destinationContainment:'pathname-revalidated-non-atomic'}.
11-12. converter:subscribeProgress / unsubscribeProgress. No payload. Adds or removes event.sender (reference-counted) in the push registry. The sender must have send(channel, payload) and once('destroyed', fn); isDestroyed() and removeListener() are optional.
13. converter:runBenchmark [runConverterBenchmark(request, onProgress)]. Request keys allowed: codec, codecs (1-2 of h265/av1, default [codec], default codec h265), sourceRoot (realpath'd, or null), profileId (default balanced), bitrateKbps, qualityLevel, verifyMode (default quick).
   - Returns {...first successful run, codecs:[ {codec, encoder:{family,codec,hardware}, clips, results:[{level,clips,completed,failed,failures[],seconds,filesPerMinute,savedPercent,verifySecondsPerClip,fps,ok}], best, verifyComparison:[{verifyMode,...same fields}]} or {codec, error:'UNSUPPORTED'|code, encoder:null, results:[], best:null, clips:0} ]}.
   - Errors: BENCHMARK_ACTIVE, JOB_ACTIVE, BENCHMARK_SOURCE_REQUIRED, CANCELLED.
   - Long-running: minutes to tens of minutes.
14. converter:cancelBenchmark. No payload. Aborts the benchmark; returns null.
15. converter:getAuto. Returns {settings:{enabled, intervalMinutes ∈ {15,30,60,180,360,720,1440}, window:{startHour,endHour}|null, keepRunning, openAtLogin, config:startConfig|null}, status:{lastCheckAt, nextCheckAt, lastNewFiles, lastJobId, activeJobId, pausedForWindow, checking, error}}.
16. converter:setAuto. Request {enabled:boolean, intervalMinutes, window?:{startHour 0-23, endHour 0-23, not equal}|null, keepRunning:boolean, openAtLogin:boolean, config?}. config is validated exactly like start when enabled; AUTO_CONFIG_REQUIRED if enabled without one. Returns the auto state.
17. converter:checkAutoNow. Runs a tick now. Returns the auto state.

PUSH EVENTS (main to renderer):
- 'converter:progress', broadcast to all subscribed senders. Payload {jobId, revision, snapshot}, where snapshot is one of:
  (a) a full sanitized job snapshot, emitted after every store transition. Verified keys: config, counters, createdAt, discoveryComplete, id, items, revision, schemaVersion, state, summary, timings, updatedAt, plus activeItemId/failure/recovery/replacementPhase/pausedMs when set. Item keys: id, state, kind, group, eventId, relativePath, sourcePath, sourceBytes, mtimeMs, timestampKey, camera, eligibleVideo, outputPath, outputBytes, attempts, encoder, resultCode, failure. Any key matching /telemetry|sei|nal|payload|owned|publication|stdout|stderr|stack|exception|process|runner/i is stripped. With more than 256 items the list is truncated and itemCount, itemStateCounts{queued,completed,skipped,failed,active}, cleanupPendingCount and itemsTruncated are added.
  (b) live encode progress: {id, revision, progress:{phase:'continue'|'end', outTimeUs?, fps}}, where fps is the sum across workers, reported only for the lead item.
  My separate-mode run of 2 clips produced 62 snapshot pushes and 6 progress pushes.
- 'converter:benchmarkProgress', sent only to the sender that invoked runBenchmark. Shapes: {step:'scan'}; {step:'copy', index, total, codec, codecIndex, codecTotal}; {step:'run', level, index, total, encoder, hardware, codec, codecIndex, codecTotal}; {step:'verify', verifyMode, level, index, total, codec, ...}.
- The auto-convert status has no push channel. The renderer polls getAuto every 30 s (footageConverter.js L1215).

SERVICE-LEVEL EVENTS (jobService emit L298, before IPC filtering): snapshot, progress, started, pause_requested, paused, resumed, paused_network, network_reconnected, cancelled, completed{summary}, item_timing{itemId, relativePath, encoder, outputPath, sourceBytes, outputBytes, attempts, phases{inspect,source,timeline,encode,metadata,verify,saveWait,save,cleanup}, totalMs}, summary_dismissed, interrupted_save_released{pending}, recovered, recovery_failed{code}, discarded. Only snapshot and progress cross IPC; runtime.js uses item_timing for the timing log and onClipConverted.

NODE APIs (what a server would call):
- createConverterRuntime(opts) returns a frozen object: {service, store, stagingManager, capabilities, runBenchmark(req), cancelBenchmark(), start(), sweepLeftoverSnapshotFolders(), auto:{get, configure, checkNow, subscribe(listener) -> unsubscribe}, shutdown()}.
- service: {start, get, list, pause, resume, cancel, discard, retryFailed, dismissSummary, recover, continueRecovery, shutdown, subscribe(listener) -> unsubscribe, whenIdle(id)}.
- registerConverterIpc({ipcMain:{handle,removeHandler}, dialog:{showOpenDialog}, service, capabilities, benchmark:{run,cancel}, auto, fs?, pathApi?, platform?}) returns {channels, capabilities, unregister()}. Each handler is called as handler(event={sender}, payload).
- createConverterLifecycle({app:{quit}, initialize, onError}) returns {start, beforeQuit(event{preventDefault}), runtimePromise, isQuitting}.

Job states: discovering, waiting, staging, encoding, writing-telemetry, verifying, copying, replacing, paused, paused_network (all active), plus completed, skipped, failed, cancelled.

Item resultCodes: converted, completed-cleanup-pending, copied, asset-retained, no-savings, already-converted, cleanup-pending, recovery-required, plus failure codes in lowercase-hyphen form (encoder-failed, destination-collision, unsupported-codec, source-changed, verification reasons, ...).

### electronAndOsDependencies

CONVERTER DIRECTORY: `grep require(` finds no electron import in any of the 22 files. Dependencies are Node builtins only:
- fs.promises: lstat/stat with {bigint:true} (dev/ino identity), realpath, statfs {bigint}, link, rename, open 'wx'/'r+'/'a', FileHandle.sync, truncate, mkdtemp, chmod, rm, rmdir;
- crypto (sha256, randomUUID), path, os.tmpdir (default only), child_process.spawn (passed in as options.spawn), performance.now, AbortController.

The one outside dependency is the dynamic import('../../shared/teslaFilename.mjs') in scanner.js L19. In a plain Node server each of these needs nothing.

WINDOWS-ONLY CODE (inert on Linux, but its absence is the problem):
- filesystemTransactions.js L24 enables windowsOwnedCleanup.js/.ps1 only when platform and process.platform are both win32 and fs is the real node fs. That module spawns powershell.exe and uses Win32 handle APIs for an ownership-verified rename with no replace and a delete guarded by a locked final.
- On Linux the fallback is removeOwned {atomicOwnershipCheck:false, remove() -> unsupported} and renameExclusive {atomicNoReplace:true, atomicExpectedOwnership:false, promote = link(), refuses removeSource}.
- Consequences: replacement is unavailable, no owned file is ever deleted, and every cleanup becomes cleanup-pending.
- A Linux server needs its own injected removeOwned/renameExclusive. See portPlan.
- runtime.js createVolumeInfo L403-421: the win32 branch uses PowerShell DriveInfo. On Linux it uses statfs f_type (CIFS 0xff534d42, SMB2 0xfe534d42, NFS 0x6969, ...) and works unchanged.
- Windows-specific path handling (lowercased comparisons, UNC detection, WINDOWS_RESERVED_NAME id checks, windowsHide spawn option) is harmless on Linux.

ELECTRON TOUCHPOINTS (all outside the converter directory), with what each needs in a headless Linux Node server:
1. main.js L226-237 `app.getPath('userData')` (gives <userData>/converter-jobs, converter-auto, converter-logs) and `app.getPath('temp')` (gives <temp>/sentry-six-converter and <temp>/sentry-six-verification-*). Server: environment variables DATA_DIR (e.g. /data) and WORK_DIR (e.g. /work), both on persistent local volumes.
2. main.js L221-225 findFFmpegPath()/findFFprobePath() from src/main/ffmpeg.js. That module uses electron `app` (isPackaged/getAppPath/resourcesPath), and the bundled ffmpeg_bin binaries are macOS Mach-O. Server: do not import ffmpeg.js; pass '/usr/bin/ffmpeg' and '/usr/bin/ffprobe', overridable through FFMPEG_PATH/FFPROBE_PATH.
3. main.js L241-248 registerConverterIpc({ipcMain, dialog, ...}). Server: a fake ipcMain (a Map of channel to handler) and a dialog shim whose showOpenDialog({defaultPath}) returns {canceled:!defaultPath, filePaths:[defaultPath]}. The browser picks the folder in its own folder-browser modal and sends the choice as defaultPath; ipc.js still validates and realpaths it. Proven in probe-linux.js.
4. ipc.js event.sender (a WebContents: send, once('destroyed'), isDestroyed, removeListener). Server: a per-browser-connection SSE (or WebSocket) object implementing send(channel, payload) by writing an `event: <channel>` frame, once('destroyed', fn) via res.on('close', fn), and isDestroyed() via res.writableEnded. Each HTTP invoke carries a client id so the handler receives {sender: that connection}. This is required for benchmark progress routing.
5. runtime.js createConverterLifecycle (L912) needs only app.quit() and event.preventDefault(). main.js L2212 calls beforeQuit from app 'before-quit'. Server: app = {quit: () => process.exit(0)}; on SIGTERM/SIGINT call lifecycle.beforeQuit({preventDefault(){}}), which awaits runtime.shutdown() (kills ffmpeg, persists paused state) and then calls app.quit.
6. runtime.js startConverterWithRecoveryPrompt (L984) uses dialog.showMessageBox (Retry/Quit) and app.quit. Server: replace it with a loop that calls lifecycle.start() with backoff, logs the error code, exposes 'converter recovery failed' on a health/status endpoint, and keeps the converter HTTP routes closed until start() resolves. This keeps the desktop rule that no converter IPC opens before recovery succeeds.
7. main.js L140-213 Tray, Menu, nativeImage, app.setLoginItemSettings, getLoginItemSettings and --background implement auto-convert keepRunning/openAtLogin. Server: not needed, because the server is always running. The settings still round-trip because setAuto requires both booleans; they are simply ignored. Whether the UI shows those two toggles is a product decision, since the user wants the Encoder tab to look identical.
8. main.js L2137 app.requestSingleInstanceLock() stops two converters from using the same job files. jobStore has no cross-process lock. Server: run one container per DATA_DIR, or take an exclusive lock file at startup.
9. main.js L235 onClipConverted calls getClipThumbnails()?.prewarm (the clipThumbnails subsystem). Optional; wire it to the web thumbnail cache or omit it.
10. preload.js L37-80 contextBridge/ipcRenderer. Server: a browser module defining window.electronAPI (or passing an equivalent `api` object to initFootageConverter; script.js L1597 already passes `api: window.electronAPI`) with identical method names and signatures, implemented with fetch POST plus EventSource. Keep the reference-counted subscribe/unsubscribe from preload L63-80.

### linuxDockerGaps

1. OWNERSHIP ADAPTER MISSING (critical). Measured in this sandbox, which matches the target stack: Ubuntu 24.04, ffmpeg 6.1.1-3ubuntu5.
   - capabilities are hardlink-cleanup-pending / unavailable / unavailable.
   - (a) Replace mode is refused (REPLACEMENT_UNAVAILABLE) and the UI disables it (footageConverter.js L496-509).
   - (b) Separate mode completes with resultCode completed-cleanup-pending and leaves `<out>.mp4.sentry-six-<job>-<item>-<nonce>.partial` (a hard link to the output) next to every output.
   - (c) Each clip leaves a full output copy in <temp>/sentry-six-verification-*/<uuid>.mp4.
   - (d) With staging (networkMode staging, or auto with an SMB source) each clip also leaves a full source copy in <temp>/sentry-six-converter/<job>-<item>-<nonce>-source.mp4.
   - Neither sweep ever removes (c) or (d): the job manifests keep referencing them, and the sweep only deletes folders no job points to. A multi-TB archive therefore fills WORK_DIR.
   - Fix: inject a POSIX removeOwned {atomicOwnershipCheck:true, guardedRemoval:true, remove({target, expected:{device,inode,size,sha256}, guard?})} and renameExclusive {atomicNoReplace:true, atomicExpectedOwnership:true, promote({from, to, expectedSource, removeSource})} through createConverterRuntime options. No change to staging.js is needed.
   - Verified with a minimal adapter (probe-linux.js posix mode): all capabilities become available, replace converted the originals to HEVC in place, and no TEMP-/BACKUP-, .partial, staged or snapshot files remained.

2. ATOMICITY ON LINUX/SMB.
   - Node has no renameat2(RENAME_NOREPLACE) and no unlink-if-identity-matches. A link()+unlink() promoter works on ext4/xfs, and on SMB only if the server supports hard links. Linux CIFS supports hard links on SMB2/3 when the server filesystem does (NTFS, Samba), but this must be tested on the actual NAS.
   - Without hard links, separate publication to an SMB destination fails: link() returns EOPNOTSUPP, which becomes DESTINATION_WRITE_FAILED, or EPERM, which becomes a misleading DESTINATION_COLLISION.
   - Recommendation: a small native helper built in the image (a C program, about 150 lines, with the same JSON-on-stdin protocol as windowsOwnedCleanup.ps1).
     - rename: open with O_NOFOLLOW, fstat, check dev/ino/size, hash with sha256, then renameat2 with RENAME_NOREPLACE.
     - remove: verify the same way, renameat2 to a private quarantine name with RENAME_NOREPLACE, re-open and fstat to confirm it is the same inode, then unlinkat; if it does not match, rename it back.
     - guard: hold the final open, verify it, delete the backup, then re-verify the final.
   - I believe the Linux CIFS client implements RENAME_NOREPLACE as a server-side no-replace rename (cifs_rename2). Verify this on the target share.
   - These guarantees are weaker than the Windows handle-based ones, because there is a small time-of-check/time-of-use window. That is acceptable in a single-writer container, but the owner should approve it given the insurance requirement.

3. DEVICE AND INODE IDENTITY ACROSS REMOUNTS.
   - Manifests persist device/inode for expectedSource and for files on the share (destinationPartial, replacementCandidate, replacementBackup). On CIFS, st_dev is an anonymous device number allocated per mount, so it changes when the share is remounted. I am fairly sure of this.
   - A Docker `local` volume with driver_opts type=cifs remounts on every container restart.
   - Items in flight on the share at crash time then fail identity checks after the restart, which ends in UNSAFE_OWNED_PATH, manual-intervention or cleanup-pending. This fails safe (the backup and original are kept) but is noisy.
   - Mitigation: mount SMB on the host (fstab or systemd automount) and bind-mount it into the container, so container restarts do not remount. Use `serverino` (the default) so inode numbers are stable. With `noserverino`, inodes are client-generated and the before/after identity checks during a copy can fail.
   - Mounting CIFS inside the container needs CAP_SYS_ADMIN and is not recommended.

4. NETWORK ERROR CODES.
   - RETRYABLE_PATH_CODES (runtime.js L32) are ENOENT, ENOTCONN, ENETDOWN, EHOSTUNREACH, ECONNRESET, ETIMEDOUT, EIO.
   - Linux CIFS soft mounts (the default) can also return EHOSTDOWN, ESTALE or EAGAIN. Those would fail the clip instead of entering paused_network.
   - Inject options.network = {isRetryable: an extended set, checkPath: the same as the default} instead of editing runtime.js.

5. GPUs (Ubuntu ffmpeg 6.1.1, checked here):
   - Encoders present: hevc_nvenc, av1_nvenc, hevc_qsv, av1_qsv (via --enable-libvpl), hevc_vaapi, av1_vaapi, libx265, libsvtav1, libaom-av1. No hevc_amf or av1_amf. Hwaccels: cuda, vaapi, qsv.
   - NVIDIA: requires NVIDIA_DRIVER_CAPABILITIES to include video (plus compute,utility); otherwise libnvidia-encode/libnvcuvid are missing and the planner silently falls back to libx265. av1_nvenc needs an Ada-generation (RTX 40) or newer GPU. NVENC session limits on consumer cards turn high concurrency into encoder-failed, then a CPU fallback. Run the benchmark.
   - AMD (including APUs): the AMF probe fails because the encoder is not built, so AMD uses VAAPI. Needs mesa-va-drivers (radeonsi) and access to /dev/dri.
   - Intel: VAAPI needs intel-media-va-driver-non-free (multiverse). QSV through libvpl likely also needs the Intel GPU runtime (libmfx-gen1.2 / libvpl2). The planner probes each, so missing pieces only mean a fallback.
   - /dev/dri/renderD128 is hardcoded (encoderPlanner.js L96, L140, L178, L228; runtime.js does not pass vaapiDevice). On multi-GPU hosts, map the desired render node to /dev/dri/renderD128 inside the container, or add a vaapiDevice option (a small fork of runtime.js L511 and jobService runChild L725).
   - The container user needs the host's render/video group IDs (group_add).

6. VOLUMES AND DISK.
   - DATA_DIR and WORK_DIR must be persistent and local, not SMB and not the container's overlay /tmp, so crash recovery finds its staged files and snapshots.
   - Keep WORK_DIR on one filesystem: the verifier moves the candidate from <work>/sentry-six-converter into <work>/sentry-six-verification-* with rename, and falls back to a copy otherwise.
   - Staging requires free space of source + output + 512 MiB per clip (checkStagingSpace). Replace mode requires output + 512 MiB free next to the original on the share.

7. MEMORY. Whole files are read into memory: readTimeline readFile(source), the writer's handle.readFile(candidate), and the verifier's readFile of the candidate and of the source. Expect roughly 2-3x the clip size per active worker. Size the container memory limit for the chosen concurrency (5 by default).

8. TIME ZONE. The auto-convert window uses new Date().getHours() (local time). Set the TZ environment variable and install tzdata, or the container uses UTC.

9. SIGNALS. Use init: true (tini) to reap ffmpeg children and deliver SIGTERM, plus an explicit SIGTERM handler. Set stop_grace_period to at least 60 s: shutdown waits for every job's run to finish persisting, and the Docker default of 10 s may cut it off, after which the next start goes through recovery.

10. HTTP AND PROXY TIMEOUTS. runBenchmark (minutes), cancel and discard (up to 30 s) hold their request open. Node's own server is fine (server.timeout is 0 by default), but reverse proxies (nginx 60 s, Cloudflare 100 s) will cut these requests. Raise proxy_read_timeout, or have the web shim implement runBenchmark as a POST that returns immediately plus a result event over SSE.

11. SECURITY. The IPC layer accepts any absolute path. The HTTP layer must authenticate users and restrict sourceRoot, destinationRoot, defaultPath and benchmark sourceRoot to allowed roots (e.g. /footage, /output), before forwarding converter:start, setAuto.config, chooseFolder and runBenchmark.

### portPlan

GOAL: run src/main/converter/** byte-identical to ai-testing and replace only main.js's wiring and preload's transport.

1. VENDOR AS-IS (no edits): all of src/main/converter/* (including windowsOwnedCleanup.*, which is inert on Linux) and src/shared/teslaFilename.mjs, keeping the src/main/converter and src/shared layout so the relative import still resolves. Pull them in with a git subtree, submodule or sync script from the ai-testing branch, and add a CI check that diffs the vendored tree against upstream. Also reuse the tests: tests/main/converter/*.test.js plus fixtures run under jest on Linux. The real-ffmpeg integrationE2E suite uses realRuntime.js, which already injects POSIX adapters.

2. NEW SERVER FILES (web repo only):
   a) server/converter/host.js replaces main.js L215-255 and L2175:
      - Build `lifecycle = createConverterLifecycle({ app:{quit:()=>process.exit(0)}, initialize: async ({retainRuntime, runtime, isQuitting}) => {...} })`.
      - Inside initialize: `rt = runtime || await createConverterRuntime({ userDataPath: DATA_DIR, tempPath: WORK_DIR, ffmpegPath: process.env.FFMPEG_PATH||'/usr/bin/ffmpeg', ffprobePath: ..., spawn, fs, pathApi: path, platform: process.platform, removeOwned, renameExclusive, network, onClipConverted })`.
      - Then retainRuntime(rt), await rt.start(), registerConverterIpc({ipcMain: fakeIpcMain, dialog: dialogShim, service: rt.service, capabilities: rt.capabilities, benchmark:{run: r=>rt.runBenchmark(r), cancel: ()=>rt.cancelBenchmark()}, auto: rt.auto}), and return rt.
      - Start-up: a retry loop around lifecycle.start() replaces startConverterWithRecoveryPrompt; converter routes stay at 503 until it resolves.
      - Shutdown: process.on('SIGTERM'/'SIGINT', () => lifecycle.beforeQuit({preventDefault(){}})).
      - Startup lock file on DATA_DIR to keep a single instance.
   b) server/converter/posixOwnedFs.js: Linux removeOwned/renameExclusive with exactly the contracts staging.js expects. Field and return names:
      - remove({target, expected:{device,inode,size,sha256,...}, allowIdentityAlias?, guard?:{target, expected}}) returns {removed:true} | {removed:false, missing:true} | {removed:false, ownershipMismatch:true[, guardMismatch:true]}.
      - promote({from, to, expectedSource:{device,inode,size,sha256}, removeSource}) returns {atomicNoReplace:true, sourceRemoved:boolean[, ownershipMismatch:true]}. It throws EEXIST on collision and ENOENT if the source is missing.
      - Phase 1 (fast, JS only): lstat/open identity + sha256 checks with link()+unlink(), as in probe-linux.js. DECIDING WHAT TO CONVERT AND AVOIDING DOUBLE CONVERSION:
1. The scanner yields only Tesla-named .mp4 files (/^\d{4}-\d{2}-\d{2}_\d{2}-\d{2}-\d{2}-(.+)\.mp4$/i) plus Saved/Sentry event assets. includedGroups filters group folders only; non-group folders are walked too.
2. Within a job, duplicates are removed by relativePath + sourcePath.
3. ffprobe codec: h265/av1 is skipped as already-converted; this covers replaced files and re-runs.
4. Auto-convert keeps an index of handled clips by size and mtime. In separate mode a clip whose destination file exists is treated as known. A clip that fails 3 times is given up. After a replace, the new file's size and mtime are recorded.
5. Separate publication never overwrites (DESTINATION_COLLISION).
6. Replace mode re-fingerprints the original (sha256 + dev/ino/size) right before backing it up, and refuses with SOURCE_CHANGED if it changed after the encode.

PARALLELISM:
- Only one job is active per process (startUnlocked checks every manifest).
- Within a job: one producer (scanner look-ahead 16, batches of 200 items or every 250 ms, queue limit 10,000) and N workers (config.concurrency 1-64; missing means 1; the UI recommends 5; the runtime allows up to 64 leases).
- Inspect, stage, encode, telemetry and verify run in parallel. Publish/replace is serialized (acquireCommit), so the job-level recovery fields always describe one 'lead' item. Other in-flight items keep their ownership on the item itself and are cleaned up and re-queued on recovery (releaseInterruptedItems).
- Encode fallbacks: zero-copy GPU decode, then GPU decode, then CPU decode, then CPU encoder, at most 3 recorded attempts. Size-profile misses get one bitrate retry (two for libaom).
- The benchmark is mutually exclusive with jobs and with auto-convert checks.

CRASH RECOVERY (runtime.start, L854):
- Every manifest in an active state goes through store.recover(id, inspectRecovery). The inspector reports facts: candidateExists, partialExists, finalExists, sourceExists, backupExists, finalValid (sha256 match), partialFinalSameIdentity. The manifest becomes paused with a recovery action:
  - discovering/waiting: resume-discovery or resume-queue;
  - encoding-type states: restart-encoding or cleanup-and-restart-encoding, or manual-intervention if anything exists at the destination;
  - copying: copy truth table 000=restart-copy, 011=finalize-copy, 100=resume-copy;
  - replacing: a per-phase truth table over candidate/source/backup/finalValid, giving backup-original, promote-candidate, validate-final, restart-replacement, restore-backup, delete-backup, finish-replacement or rollback-complete, otherwise manual-intervention.
- Then, in order: auto.start, the sweeps, then the deferred recoveries execute serially (continueRecovery).
- In separate mode, Resume or Cancel of a job interrupted mid-save cleans up and re-queues (releaseInterruptedSave). In replace mode, Cancel first re-inspects the replacement and resolves it if the facts are unambiguous.
- paused_network: exponential backoff from 1 s to 30 s polling fs.access on the affected path (or its nearest existing ancestor for destinations).

AUTO-CONVERT:
- Ticks every 30 s (unref'd timer).
- When a check is due, inside the window and not busy: sweep (a full scan, counting unknown files). If there are new files, service.start({...config, autoConvert:true}); the producer then skips known clips.
- It follows its own job: outside the window it pauses the job (recorded in state.json) and resumes only a pause it made itself. When the job ends, results are recorded into the index.
- It adopts a still-running automatic job after a restart.

### risks

- Insurance/telemetry: on Linux the default code never deletes anything, so telemetry is never lost by the converter, but replace mode is blocked and temp space leaks. The POSIX adapter that unblocks replace mode is the one place where the web build's safety guarantees are weaker than the Windows handle-based ones. It is a short check-then-act window, acceptable only with a single writer per share. Needs explicit owner sign-off and a real-SMB crash test (kill -9 during each replacement phase, then restart).
- Leaked temp data without the adapter: about source + output bytes per clip when staging from SMB, never reclaimed, enough to fill WORK_DIR on a large archive. Must not ship the web build without the injected adapter.
- Hard links on the SMB destination: separate-mode publication uses link(). A NAS without hard-link support fails every clip with DESTINATION_WRITE_FAILED, or a misleading DESTINATION_COLLISION for EPERM. Test on the real share.
- Remount changes st_dev on CIFS (believed). Persisted device/inode identities for files on the share then mismatch after a container restart that remounts, so in-flight items land in manual-intervention or cleanup-pending. Mitigate with a host-level mount, bind-mounted into the container, using serverino.
- A job paused in manual-intervention (or any paused or active job) blocks all new jobs, auto-convert and the benchmark (JOB_ACTIVE) until the user resolves or discards it. For a 24/7 server, surface this prominently.
- Re-running a manual separate-mode job to the same destination re-encodes every clip, then fails each at publish with destination-collision. Only auto-convert pre-checks that the destination exists. This wastes GPU time but is safe.
- jobStore keeps every finished job forever, and store.list() parses all manifests (up to 64 MiB each) on start, getCurrent, discard and auto isBusy (every 30 s while busy). Startup and the UI slow down over months without a retention policy.
- Whole-file in-memory processing (about 2-3x clip size per worker) at concurrency up to 64 can trigger the container's out-of-memory kill. Cap concurrency in the web UI, or size memory accordingly.
- The VAAPI render node is hardcoded to /dev/dri/renderD128. On multi-GPU hosts the wrong device may be used, so the planner silently falls back to another encoder or the CPU.
- Missing NVIDIA_DRIVER_CAPABILITIES=video, or missing VAAPI/libvpl runtime packages, also make the planner fall back silently to libx265/libsvtav1, which is much slower. Only the benchmark and the per-item `encoder` field reveal it.
- Linux CIFS soft-mount errors (EHOSTDOWN/ESTALE/EAGAIN) are not in the retryable set, so a NAS outage fails clips instead of pausing for the network, unless `network` is injected.
- Long-held HTTP requests (runBenchmark, cancel, discard) are cut by reverse-proxy timeouts if the IPC-over-HTTP mapping is kept 1:1.
- The IPC layer trusts any absolute path. The web layer must add authentication and a path allowlist, or any LAN user could make the converter read or write arbitrary container paths, including replacing files in place.
- Two server instances on one DATA_DIR would corrupt job manifests, because jobStore has no cross-process lock. The desktop relies on Electron's single-instance lock.
- Docker's default 10 s stop grace period may cut shutdown persistence. The next start then runs crash recovery, which is designed for this but adds risk mid-replacement.
- The UI's auto-convert keepRunning/openAtLogin toggles have no meaning on a server. Keeping the Encoder tab identical means showing controls that do nothing, unless the product owner accepts hiding them.

### summary

The worktree is checked out at commit 0b53daa, which is the tip of remotes/origin/ai-testing ("ci: telemetry tests pass and now count toward the build"). Nothing in src/main/converter/ requires electron, so the whole converter core (encoder planner, telemetry writers and inspectors, MP4 parser, verifier, snapshots, job service, runtime) is plain Node. I ran it end to end on this Linux box with Node 22 and Ubuntu 24.04's ffmpeg 6.1.1-3ubuntu5, using a synthetic Tesla-style H.264 clip: 48 frames, 40 SEI events, and a deliberate telemetry gap. For libx265, libsvtav1 and libaom-av1 the steps all worked: encode with the planner's exact arguments, inject telemetry, then verify in Off, Quick and Full. Every source Tesla SEI NAL was found byte-for-byte in the output. So H.265 and AV1 conversion is not blocked on Linux. The only thing missing is AMF (AMD's Windows API, which Ubuntu's ffmpeg is built without). On Linux, AMD (dGPUs and APUs) and Intel encode through VA-API instead (hevc_vaapi / av1_vaapi). Both are already in the planner's Linux list and are present in Ubuntu's ffmpeg. Ubuntu's Mesa VA driver is built with all codecs, including the RDNA3/RDNA4 encoders and AV1 support.

Encoder selection (encoderPlanner.js). CANDIDATES (L14-27) are tried in order: hardware candidates for the platform first, then CPU. The list ffmpeg advertises (`ffmpeg -hide_banner -encoders`) is the first filter. Each advertised candidate must then pass a real 4-frame MP4 test encode, using the same buildEncodeArgs as real jobs, before it can be chosen. The first one that passes is cached for the life of the process. If a real encode fails, the job retries in this order: GPU decode with frames kept on the GPU (NVENC only), then GPU decode, then CPU decode, then the CPU encoder. Telemetry is never re-encoded. The original Tesla H.264 SEI NAL units (Tesla's per-frame telemetry messages) are copied into the new file:
- H.265: each sample gets three inserted NALs: a standard prefix SEI (type 39, "Sentry-Six-Tesla" UUID, wrapping the whole original NAL), a type-51 compatibility NAL (0x66 0x01 followed by the original NAL from its third byte on), and a 3-byte picture marker (type 48).
- AV1: the original NALs plus one picture marker per frame, as 4-byte length-prefixed records, go in a first, unreferenced `mdat` box. Chunk offsets are rewritten to match.

Verification (verifier.js). Off only checks that the saved file hashes to what was encoded, that it is smaller than the original, and the size-profile window. Quick re-reads the original and re-extracts its telemetry, probes the output with ffprobe, and checks frame count, dimensions and duration. It then compares telemetry frame by frame: the SHA-256 of every Tesla payload, in order, plus gap ranges and transitions. Full adds a complete decode with `-xerror -err_detect explode`. In my tamper tests, Off accepted an output with all telemetry missing and an output with one SEI byte flipped. Quick rejected both (telemetry-invalid / telemetry-mismatch). Off can never replace an original, because three separate layers force Quick when replacing: the UI, the IPC start check (ipc.js) and the job service (contracts.js). In "separate output" mode, though, Off can produce telemetry-less copies. That matters for the planned file manager.

1. The VA-API render node is hard-wired to /dev/dri/renderD128 in production. runtime.js L511-515 creates the planner without vaapiDevice, jobService.js L728 calls buildEncodeArgs without it, and runtime.js L589's decodeAccel lambda does not pass it. 3. Quality mode is wrong for av1_vaapi. ffmpeg 6.1's av1_vaapi has no `-qp` option (verified with `-h encoder=av1_vaapi`), and an unknown -qp only produces the warning "Codec AVOption qp ... has not been used", which I reproduced. 6. Temp space. Staging and verification snapshots should be on one local volume (snapshot adoption is a rename on the same filesystem), not on the SMB share.

### details

How telemetry is carried, from code plus experiment:
- Source side: extractH264TelemetryTimeline reads every length-prefixed NAL in each avc1 sample. NALs with (nal[0]&0x1f)==6 containing a payloadType-5 SEI whose payload starts with one or more 0x42 bytes then 0x69 are kept as {nal: exact original NAL bytes, fingerprint: sha256(protobuf bytes after 0x69)}. Any other SEI is ignored. The injectors then require each record to be one canonical type-5 message (teslaSei.teslaPayload). Otherwise they throw and the clip fails, keeping the original.
- Frame association (mapTimelineToOutput):
  - By frame position when the output frame count equals the source's and is above 10.
  - Also by position when the source has exactly one extra terminal zero-duration sample; that sample's SEI is appended to the last output frame.
  - Otherwise by nearest PTS within one frame duration, avoiding gap frames.
  - H.265 is encoded with -bf 0, so decode order equals display order.
- H.265 output, per sample, prepended before the encoder's own NALs:
  1. All mapped records as standard prefix SEI NALs: header 0x4E 0x01, payloadType 5, size, 16-byte ASCII UUID 'Sentry-Six-Tesla', then the entire original H.264 NAL. HEVC emulation-prevention bytes are added over the payload.
  2. The same records as type-51 'compatibility' NALs: 0x66 0x01 followed by original_nal[2:], i.e. the size byte(s), payload with its original EPBs, and the trailing 0x80.
  3. A marker NAL [0x61 0x01 0x80] (type 48).
  - Frames with no telemetry get only the marker.
  - Samples, stsz, mdat and stco/co64 are rebuilt; stco is promoted to co64 if needed.
  - The viewer reads the type-51 records (dashcam-mp4.js L290-296). The verifier requires type-39 and type-51 fingerprints to agree in order, and the NAL types to lead as [39..., 51..., 48].
- AV1 output: a new `mdat` is inserted before the first real mdat, holding for each output frame in order its original NALs as [u32 BE length][original NAL], then [00 00 00 03 61 01 80].
  - All chunk offsets shift by its size.
  - The inspector requires: no track sample points into that mdat, the marker count equals the AV1 sample count, and every record is the exact marker or a canonical Tesla SEI.
  - Standard decoders ignore it; my full decode with ffmpeg 6.1 passed.

Verifier checks:
- Off (verifier.js L764-790): the snapshot's SHA-256 equals the bytes read; outputBytes < sourceBytes; the size-profile window, unless the clip is 2 s or shorter with a source of at least 500 kB, or the profile is custom/quality.
- Quick (L792-971 without L810):
  1. Re-read the (staged) source: stat size equals read size; re-extract the timeline and source timing; the timeline must equal the cached one from before the encode (sameTimeline: per-sample pts/duration/flag/NAL bytes/fingerprint).
  2. ffprobe the snapshot (-count_packets): exactly one video stream, codec hevc/av1 with tag hvc1/av01, nb_frames equal to nb_read_packets, empty stderr.
  3. Snapshot integrity; parse MP4 timing.
  4. Probe frames equal container samples; width/height equal across source, output stsd and probe; probe duration and source duration each within the largest output sample duration.
  5. Source vs output frame count exact, or ±1 only if VFR is proven (avg ≠ real rate, non-uniform durations on the r_frame_rate grid, max/min ≤ 16).
  6. Inspector accepted: layoutValid, tag matches, sampleCount equals container samples.
  7. Mapped event count equals source event count (no unmapped events).
  8. compareTelemetry: exactly one marker per sample; gap ranges equal; transition indexes equal; per-sample ordered fingerprint lists equal.
  9. Smaller than the source; size-profile window.
- Full adds L810: `ffmpeg -nostdin -hide_banner -loglevel error -xerror -err_detect explode [gpu decode] -i snap -map 0:v:0 -an -sn -dn -fps_mode passthrough -progress pipe:1 -nostats -f null -`.
  - Must reach progress=end with frame equal to the container sample count.
  - Only null-muxer non-monotonic DTS warnings are tolerated on stderr.
  - A GPU-decode failure is re-run on the CPU; only a CPU failure rejects. After 3 GPU fallbacks for an encoder, GPU decode stops being offered.
- On success: snapshot re-hashed, then transferred, then publicationArtifact {path, token, sha256, size}. Staging only publishes artifacts whose token the registry minted (runtime.js L264-297).

### risks

- Verify 'off' in separate-output mode accepts converted files with ALL telemetry missing or with altered SEI bytes. My tamper tests show 'OK' for both. If the web file manager lets users trash originals after an Off conversion, Tesla telemetry is lost. Replace mode is protected three times (UI footageConverter.js L403-415, ipc.js L316-319, contracts.effectiveVerifyMode L75-78 used at jobService.js L1133); separate mode plus a later manual delete is not.
- The VA-API render node is hard-wired to /dev/dri/renderD128 in production (runtime.js L511-515, L589; jobService.js L728). On multi-GPU hosts AMD/Intel may be probed on the wrong node, or the wrong GPU used. QSV has no device selection at all.
- av1_vaapi quality mode passes '-qp', which ffmpeg 6.1 ignores with only a warning. The selected quality level has no effect on AMD/Intel AV1. Files can come out larger than the original and end as KEEP_ORIGINAL.
- Replacing originals is 'unavailable' on Linux as coded: filesystemTransactions.js L25-47 has guarded delete and rename only on Windows. Owned temp cleanup is also reported 'unavailable' on Linux. Outside my area but it blocks any in-place replace feature in Docker.
- NVIDIA in Docker needs NVIDIA_DRIVER_CAPABILITIES to include 'video'. The toolkit default omits libnvidia-encode/libnvcuvid, so NVENC fails and everything silently falls back to the CPU. The host driver must also meet ffmpeg 6.1's NVENC API floor (exact number not verified here; probably 530.41+).
- Consumer NVIDIA NVENC session caps (about 8 concurrent) versus converter concurrency up to 64. Excess clips fail to encode and fall back to libx265/libsvtav1 per clip (slow, not unsafe).
- The planner proves encoders only in bitrate mode with system-memory frames. Quality-mode or GPU-decode incompatibilities surface during real jobs and degrade to CPU per clip without user-visible explanation beyond the item's 'encoder' field.
- AMD VCN alignment (64x16) versus Tesla HW4 sizes 2896x1876 and 1448x938: if ffmpeg 6.1's av1_vaapi or hevc_vaapi writes padded dimensions, the verifier rejects the clip with dimension-mismatch, which is safe but means no conversion. I could not test without hardware.
- AV1 hardware encode only on RDNA3/RDNA4 (incl. 780M/760M/880M/890M APUs), Ada/Blackwell, Arc/Meteor Lake+. Intel Xe2 may need a newer intel-media-driver than Ubuntu 24.04's 24.1.0 (unverified). Everything else falls back to libsvtav1.
- Memory: whole-file Buffers in the writers, timeline extraction and verifier (several copies per clip). High concurrency in a memory-limited container can hit OOM; the mp4 code also cannot handle files over 2 GiB (readFile limit), but Tesla clips are far smaller.
- Writer timing (converterAdapters.js L10-15, truncating µs) and verifier timing (verifier.js L345-356, rounding) differ slightly. In timestamp-mapping mode, used for clips of 10 frames or fewer or with frame-count drift, this could make a valid clip fail with telemetry-mismatch. Fails safe.
- Quick never decodes the video bitstream: a corrupt but well-formed output can pass Quick (telemetry is still fully checked). Only Full proves decodability.
- Telemetry fingerprints are SHA-256 of the Tesla protobuf payload, not of the whole NAL. Byte-identity of the surrounding SEI framing is guaranteed by construction (copied verbatim) and canonical-form checks, but it is not compared as a full NAL against the source.
- Web playback of HEVC/AV1 depends on the viewer's browser, not the server: HEVC needs a platform decoder (Safari; Chrome/Edge on Windows/mac with hardware support; Firefox only on Windows), and AV1 is not supported on Safari without hardware AV1. Telemetry parsing (dashcam-mp4.js) is pure JS and works anywhere. This is probably the source of the 'can't handle hevc' confusion: the user's Electron/Chromium had a platform HEVC decoder.

## map:viewer

### summary

The viewer is one page: src/renderer/index.html plus the ES-module script.js (5,266 lines) and its scripts/* modules. It indexes a TeslaCam folder into clip groups (core/teslaCamIndex.js buildTeslaCamIndex, then shared/dashcamCollections.mjs buildDashcamCollections), lists them in the sidebar tabs Clips / Drives / Converter (footageConverter.createSidebarPanelSwitcher, which accepts only 'clips','drives','converter'), and plays a collection with up to 6 synchronized HTML5 <video> elements. One master camera drives the timeline (nativeVideo at script.js:4309, loadNativeSegment at 4671, syncMultiVideos in ui/multiCamFocus.js). Telemetry is read separately from the video. The master camera's whole MP4 is fetched into an ArrayBuffer and parsed in plain JS by DashcamMP4 (scripts/data/dashcam-mp4.js) with protobuf.js and proto/dashcam.proto. The result, [{timestampMs, sei}], is read about 60 times a second (requestAnimationFrame telemetry loop) to drive the dashboard, g-force meter, compass, steering wheel and the Leaflet map.

The user is right: H.265 and AV1 play in the app today. Nothing in the renderer uses WebCodecs any more. Leftover pieces remain: player.decoder at script.js:3956 and 4033, s.decoder?.close() at 3238, a comment in state.js:66, and the codec/description/data fields that DashcamMP4 still returns, but nothing creates a VideoDecoder. state.ui.nativeVideoMode is always true (state.js:92, script.js:3531). Decoding is done by Chromium's own <video> pipeline. Electron 39 (Chromium 142) decodes H.264, AV1 (dav1d, in software on every OS) and HEVC (hardware decoder: D3D11 / Media Foundation on Windows, VideoToolbox on macOS). That is why the converted files opened on the user's machine. What the ai-testing branch changed in dashcam-mp4.js (commit fab19c3) is the telemetry parser: it now reads the converter's H.265 compatibility records and markers and its AV1 telemetry block. In a web version the video is decoded by the viewer's browser, not inside the container, so the container needs no HEVC/AV1 decoder for playback. The container's ffmpeg only decodes for thumbnails, export and the converter.

How footage is reached today. Main path (Electron): native folder dialog, then path strings, then lazy electronAPI.readDir traversal, which produces plain objects {name, path, webkitRelativePath, isElectronFile:true}. Media loads through file:// URLs made by lib/utils.js filePathToUrl(), which works because the window has webSecurity:false (main.js:304). Fallbacks (showDirectoryPicker, or <input webkitdirectory>) use real File objects and blob: URLs, with no export, delete, thumbnails or drive data. The approach with the least divergence for the web build is to make the browser look like the Electron path: inject a window.electronAPI shim backed by HTTP and WebSocket, and switch filePathToUrl() to return a Range-capable server URL. Then traversal, indexing, playback, telemetry, thumbnails, delete and export all run unchanged.

### details

How decoding and telemetry extraction work for each codec

Video decode (all codecs)
- HTML5 <video muted playsinline> elements: videoMain plus videoTL, TC, TR, BL, BC, BR. Sources are file:// URLs (Electron) or blob: URLs (browser File).
- The master is the front camera, or the first camera that has a file.
- Sync works like this: the others follow master.currentTime (syncMultiVideos); a segment advances on 'ended' (onMasterEnded); seeking maps a collection offset to a segment using probed durations (probeSegmentDurations: temporary video elements with preload=metadata, 4 at a time, 5 s timeout, LRU of 256).
- No WebCodecs anywhere.

Telemetry (DashcamMP4, which must have the whole file in memory)
- getConfig() requires exactly one stsd entry, mapped avc1→avcC, hvc1→hvcC, av01→av1C:
  - avcC and hvcC must be version 1; av1C must have marker+version byte 0x81.
  - NAL length size: from avcC byte 4 &3 +1, or hvcC byte 21 &3 +1.
  - Timestamps in ms = (stts cumulative + ctts offset) * 1000 / mdhd timescale. seiExtractor then sorts by presentation time.
- H.264 (avc1): each sample is split into length-prefixed NALs. Types 7/8 are SPS/PPS. Type 6 is SEI and goes to seiPayload: payloadType 5 (user_data_unregistered), size check, then a run of 0x42 bytes, then 0x69, then the protobuf, then the 0x80 stop bit, after removing emulation-prevention bytes. Decoded with SeiMetadata.decode; failures are skipped silently. Types 5/1 are slices (keyframe if type 5).
- H.265 (hvc1, converter output):
  - Per sample, the NAL type is (b0>>1)&63.
  - 61 01 80 is a picture marker and is counted.
  - Any other 61 01 … is an error.
  - 66 01 + body is a compatibility record: the original Tesla H.264 SEI is rebuilt as 06 05 + body, then parsed as above. Here a protobuf failure throws.
  - Type ≤31 is a picture (VCL); IRAP types 16-23 mark keyframes.
  - The standards-valid prefix SEI (4E 01, UUID 'Sentry-Six-Tesla' + H.264 SEI) is ignored by the viewer.
  - If any marker or compatibility record exists, every sample must have exactly one marker.
  - Plain HEVC files with no records parse with no telemetry.
- AV1 (av01, converter output):
  - Needs at least 2 mdats. The first mdat is the telemetry block and must not be referenced by any sample of any track (the _otherSamples check).
  - It holds 4-byte length-prefixed records: Tesla H.264 SEI NALs (06 05 …), each frame's group ending in a 61 01 80 marker. Group i belongs to video sample i.
  - The marker count must equal the sample count. Any other record throws.
  - Frame data is the raw OBU sample; keyframe is not computed.

Browser support for <video> MP4 playback (the code uses no WebCodecs). Confidence is noted on each.
- H.264: all browsers.
- HEVC (hvc1):
  - Safari macOS/iOS: yes (high confidence). The converter writes the hvc1 tag (encoderPlanner.js:126).
  - Chrome 107+ and Edge on Windows/macOS/ChromeOS/Android: yes when the client has an HEVC hardware decoder; there is no software fallback in Chrome. Medium-high confidence.
  - Edge on Windows may need Microsoft's HEVC Video Extensions (unsure).
  - Chrome on Linux: VA-API HEVC, availability depends on version and flags (unsure).
  - Firefox: recent releases (2025) added HEVC with hardware decoding, Windows first (exact versions and platforms unsure).
- AV1 (av01):
  - Chrome 70+ and Edge: yes on all desktop OSes (dav1d software, hardware where available). Edge on Windows once relied on the AV1 extension (unsure if still).
  - Firefox 67+: yes.
  - Safari 17+: only on devices with an AV1 hardware decoder (Apple M3, A17 Pro and newer); not on older Macs or iPhones.
- So for full coverage: AV1 is safest on Chrome/Firefox; HEVC is safest on Safari and on Chrome/Edge with a modern GPU.
- Electron caveat: if the user turns off hardware video acceleration in Settings (settings.js:57 appends disable-accelerated-video-decode), HEVC stops playing in the desktop app.
- WebCodecs is not needed. If it is ever brought back: VideoDecoder requires a secure context (https), and HEVC in WebCodecs is hardware-only in Chromium.

How the viewer finds footage
- traverseDirectoryElectron (2329) checks, in order:
  1. A GMC SurroundVision source (discoverGmcSource, with an adapter of {name, list}).
  2. Whether the picked folder itself is RecentClips, SentryClips or SavedClips.
  3. Child folders named recentclips / sentryclips / savedclips (case-insensitive).
  4. Otherwise loose clips, recursing one level.
- Dates are collected from RecentClips/YYYY-MM-DD folders or flat YYYY-MM-DD_ filenames, and from event folders named YYYY-MM-DD_HH-MM-SS.
- Only the newest date is loaded first (loadDateContentElectron). Picking a date in dayFilter loads that date.
- Event folders contribute *.mp4, event.json, event.png, event.mp4 and thumb.png.
- event.json is read through readFile and attached as eventMeta (reason badge, map pin, auto-seek to 15 s before the event).
- Drive mode (selectDriveCollection 1660) loads every date a SentryUSB drive spans and builds a virtual collection.

- sentryUsbDataPath auto-load at 800 ms.

### risks

- Deleting the clip that is playing: handleClipDeleted (script.js:1454) calls vid.remove() on every grid video and on videoMain, assuming the window reloads right after. If the web shim omits deleteFolderWithReload or returns reloading:false, the flow falls through to deleteFolder; for the active clip that removes the video elements and leaves the viewer black until a manual reload. Emulate the reload with sessionStorage plus checkPendingDelete.
- HTTP/1.1 connection limit: browsers allow 6 connections per host:port. A 6-camera segment plus the master-file telemetry fetch, up to 4 concurrent duration probes (probeSegmentDurations), filmstrips/thumbnails, API calls and any SSE stream can exceed that. Cameras then stall; non-master tiles give up after 3 s and the master after 5 s (loadNativeSegment). Use WebSocket for push events; consider HTTP/2 over TLS. Not yet tested here.
- Browser HEVC/AV1 support differs by browser and client hardware. There is no codec probe and no transcode fallback today. A failed master camera raises MediaError 3/4, which loadNativeSegment rejects with describeMediaError, and the user sees 'failedToLoadVideo'. A failed non-master tile stays black silently. Telemetry, the dashboard and the map still work because parsing is pure JS.
- Untested in other browsers: H.265 samples carry app-specific NAL types 48 (61 01 80) and 51 (66 01 …). Chromium (Electron) ignores them, as confirmed by the user's playback. Safari/VideoToolbox, Firefox/Media Foundation and Chrome on Linux (VA-API) should ignore unspecified NAL types per spec but have not been tried. Test real converted files in each target browser.
- Telemetry loss through remuxing (insurance): AV1 telemetry lives in an mdat that no track references. Any ffmpeg remux or faststart pass (-c copy, qt-faststart) of stored AV1 files drops it silently. The viewer never remuxes stored files, and exportConcat.prepareConcatFiles remuxes only temp copies (export telemetry comes from the renderer). The web port must never add faststart, HLS or remux steps to stored footage; transcodes and proxies must be display-only copies.
- Telemetry parsing is all-or-nothing for converted files: for hvc1 and av01, any malformed carrier record, protobuf failure or marker-count mismatch throws. extractSeiFromEntry then returns empty telemetry for the whole clip (path flow, seiExtractor.js:123-130) rather than partial data. That is correct for integrity, but surface it in the UI rather than show 'No Data'.
- In-place replacement by the converter: the in-memory telemetry cache (seiExtractor, keyed by path) and durationCache (keyed by path) can serve values from the old file; browser HTTP caches can mix byte ranges from the old and new files unless ETags change. Use strong ETags with If-Range, and clear the caches on converter completion events.
- Large export payload: exportData.seiData holds about 36 entries per second per collection (each a full protobuf object) and is sent as JSON. Long exports can be 100 MB+ and exceed default body limits or memory.
- Full-file reads: telemetry parsing loads the whole master MP4 into memory per segment (ArrayBuffer plus per-NAL slice copies). Expect higher browser memory and roughly 2x SMB reads per played segment.
- Security: readDir/readFile/media/delete accept arbitrary absolute paths in Electron. The server must confine them to configured roots after realpath (block symlink escapes and ..), and must require authentication, because the endpoints expose the footage share.
- Multi-viewer: settings.json becomes global to every browser. Export ids (export_${Date.now()}) can collide across clients. Route progress events per client.
- Electron-only features such as Leaflet-mode minimap export, OS trash, showItemInFolder and auto-update must be hidden or replaced. Otherwise their buttons fail silently in the web UI.
- Missing fonts in the container can break timestamp exports (drawtext font='Arial') and change how the ASS dashboard looks (Segoe UI).
- Edge cases in the files themselves: AV1 keyframe is always false in DashcamMP4 (harmless now, but matters if WebCodecs comes back). The Tesla filename regex accepts only .mp4. Symlinked clip files are skipped by the scans.
